# Conquest Architecture

## Overview

Conquest reimplements a legacy C text strategy game with modular C#. Phase 1, **Conquest Classic**, preserves original gameplay with a CLI. Phase 2, **Conquest Modernized**, permits improvements after a working, tested Classic baseline. See [AGENTS.md](../AGENTS.md).

The intended boundary is UI-independent game logic in Core, with input and presentation in front ends. The current implementation only partially realizes this boundary.

## Modules

The enemy turn slice is implemented in `Game.EnemyOrders.cs` and `Game.EnemyEconomy.cs`. Fully initialized Classic `BeginClassicTurn` issues C's live-slot scout/transport/warship decisions before the existing movement pass; debug Tick remains movement-only. Enemy landings update existing planets and fleets using their distinct C eligibility/one-third-room rules. Enemy combat and blast arithmetic reuse existing Core code. The common growth pass queues both owners in star/planet order: enemy investment executes automatically and player `ColonyInvestment` sessions suspend that same queue. `ResearchRules` shares tables and original enemy selection with startup, including inner/outer field rerolls. No new AI framework, strategic score abstraction or UI input system is introduced. See [source audit and safety boundaries](ClassicEnemyAI.md).

`Game.Endgame.cs` implements the separate C `check_game_over` operation. After a whole Classic turn (`up_year`), or confirmed movement-phase quit, the terminal host calls Core to evaluate active transports + owned colony IU, integer overwhelm ratios and strict final victory thresholds. `GameState.Result` holds an immutable final snapshot and prevents further movement. Pending startup/combat/investment cannot publish an outcome. Core hosts use the same explicit final check as C main; partial NotStarted development models do not automatically become full terminal games. `ClassicGameLoop` renders the original final tally and one-key exit, without owning scoring rules or changing ongoing visibility. No persistence/event framework is added. See [turn completion](ClassicEndgame.md).

`GameState` retains an enemy-processing failure reason for unsafe C paths, preventing implicit retries after partial decisions/spending. Enemy arrival/departure sets contain only player-observable events. `ClassicScreen` renders those letters in the existing event pane; enemy orders/colonization do not reveal player exploration, hidden fleet markers or colony details. Incomplete debug/test states do not acquire AI initialization implicitly. Snapshots remain incomplete and are not extended by this milestone.

### Conquest.Core

- `Game`: engine facade holding RNG/state; generates stars, finds stars by coordinates, and advances fleet movement and the turn counter.
- `GameState`: configuration, stars, two players, board sectors, visibility state, and lazily constructed `FleetSystem`.
- `Player`, `TaskForce`, `Star`, `Planet`, `Sector`, `BoardPoint`: current state models. Stars own planet collections; planets retain their parent star, ownership, population, IU, defenses and intelligence. `Ownership` matches C's enemy/player/none values. Landing, fourth-year player growth/investment/construction/research and deterministic revolt are implemented; enemy orders, colonization, economics/research and combat responses now follow ClassicEnemyAI.md, including corrected deterministic wander destination indexing.
- `Game.InitializeClassicPlayers()`: explicit Core initialization after successful `Game.GenerateStars()`. Requires fresh player/fleet state, no exploration or colonization, and no elapsed turns; rejects repeat initialization even through another `Game` facade. Establishes original attributes, configured starting transports, and the two enemy-advantage draws. Does not place fleets, grant enemy warships, make research decisions, spend player funds, or advance turns. The CLI does not invoke it automatically. A failed initialization attempt after RNG consumption requires a new state.
- `Game.InitializeClassicEnemyResearch()`: explicit next stage requiring successful completion of player initialization, not merely its started flag. `ResearchRules` applies the two-unit velocity investment without a breakthrough and selects the enemy's next `ResearchField` using the original strict comparisons, integer division, and conditional RNG draws. `GameState.EnemyResearchField` starts unset. Repeat calls are blocked by shared state across facades, including after a research RNG failure. This operation does not grant warships, select a starting star, run economy logic, or interact with the CLI. Only startup velocities 1..3 and zero enemy research progress are supported.
- `Game.InitializeClassicEnemy()`: coordinates the remaining original `initmach()` sequence after successful player initialization: assign fleet 1 one cruiser and two scouts, invoke startup research once, then score and select its starting star. Rejects empty galaxies, existing fleet/location activity, invalid board links, elapsed turns, independent research, and repeat calls before mutation or RNG consumption. Shared started/completed flags distinguish failures from successful placement; failures require a new state. `Tick()` records that turns have advanced in shared state so a new facade cannot bypass this prerequisite; existing turn counting and movement remain unchanged. `EnemyStartingStarRules` counts all stars (including self) within inclusive Euclidean range, adds one 1..5 draw per candidate in generated order, and retains the first tied maximum. The CLI does not invoke this operation automatically.
- `Game.BeginClassicPlayerStartup()`: Core-only `init_player()` session after successful enemy initialization. `GameState` owns its stage, selected star, spending balance, and pending shared-start encounter. Capacity zero requires `SelectClassicPlayerStartingStar(index)`; any generated star is allowed. Positive capacity uses `PlayerStartupRules` to repeatedly draw stars in the original order and lower the threshold by 10 after the post-increment retry test (`N+2` samples), without modifying configuration. Sampling failures leave a terminal failed session; a facade cannot restart it.
- `PurchaseClassicStartupShips` and `InvestClassicStartupResearch` operate only at the selected stationary location. Ships cost 16/6/70 for cruiser/scout/battlestar. Unaffordable requests return false without partial effects; malformed quantities, enum values, and signed-overflow cases throw before mutation. Player-only research uses all original requirement tables, progress resets, maxima, and multiple breakthroughs, without RNG or enemy decisions. The full affordable research amount is charged even beyond the cap. Remaining money is shared across facades. `FinalizeClassicPlayerStartup()` requires zero balance (including an initially zero budget without a purchase), then marks player exploration and fleet marker 1; selection alone records team-specific occupancy without revealing the star. Enemy occupancy and all planets are preserved.
- Shared starts remain valid. Finalization records `PendingSharedStartEncounter`. `PrepareSharedStartCombat` and the Classic loop resolve the encounter before movement, clearing the guard only after the complete combat pass and acknowledgements. Direct/debug ticks continue rejecting active/failed startup and pending encounters before mutation, including through new facades. See [encounters](ClassicEncounters.md).
- `FleetSystem`: debug placement, Classic orders/range/velocity, interpolation, arrival exploration/intelligence, J/N and landing. Destination retains the current star at ETA zero; null means unused. Both debug ticks and Classic begin-turn supply the game RNG to existing movement. A direct fleet tick without RNG rejects unknown unsafe arrival before mutation. `SafeExplore` mirrors C (default false). Reference rebuilding preserves crossings/colocation; collections remain authoritative. Production reuses slot initialization, exact-destination merge and empty-fleet helpers. Enemy movement reuses these helpers, while decision/combat rules remain in Game partials; see [movement](ClassicMovement.md) and [economy](ClassicEconomy.md).
- `GameConfig` and `Constants`: configuration parsing/validation and selected original constants. Some settings have no implemented gameplay consumer.
- `CRandRng`: deterministic LCG implementing `IRng`, `ISeedableRng`, and `ICRandRng`. Original sequence equivalence is not established.
- `SaveSystem`: JSON snapshot prototype for selected configuration, fog, and star fields. It omits substantial game state and does not rebuild board star links on load.
- `CommandRouter` and `GenStarsHandler`: separate command infrastructure not wired into `GameShell`. The handler prints coordinates without updating active game state.
- Star placement exists in `Game.GenerateStars`, `GameState.PlaceStars`, and the separate spacing-aware `StarGenerator`. The interactive shell uses `Game.GenerateStars`, enforcing uniqueness but not spacing and generating planets immediately after each star using the original C draw order. The other generation paths do not initialize planets or satisfy the Classic initialization prerequisite. Both state-mutating placement APIs reject regeneration once Classic player initialization starts, before changing state or consuming random draws; this guard belongs to the shared `GameState`.
- `MapRenderer` and `SectorView`: additional presentation adapters with behavior differing from the active CLI renderer.

There are no implemented `Parser`, `CombatSystem`, or `MovementSystem` classes. Earlier documentation described intended systems as existing code.

Combat is implemented in `Game.Combat.cs` and `Game.Encounters.cs`, reusing planets, weapons, game RNG and fleet lifecycle helpers. B bombardment has immediate deterministic effects. GameState owns transient fleet/enemy/player planetary sessions and a per-star combat cursor, following the investment-session pattern. Initial/final pauses, B? orders, W destinations and planetary acknowledgements suspend the turn without replaying movement/rolls across facades. Core resolves fleet battles, their required withdrawals, then immediate enemy/player planetary attacks in C order before economy and after due investment. The CLI presents the required context and cannot fall through into landing/orders during B?. Shared-start combat resolves without advancing the clock and then clears its guard. Enemy orders/investment now follow ClassicEnemyAI.md; wandering now selects the actual reachable star; scoring now follows ClassicEndgame.md; persistence remains deferred. See [combat audit](ClassicCombat.md) and [encounter correction](ClassicEncounters.md).

### Conquest.CLI

`Program` defaults to Classic initialization and the existing `ClassicStartupFlow`, then automatically enters `ClassicGameLoop`. `--debug-shell` selects the existing development shell without generating stars. `ClassicScreen` composes the original map/panes from Core state, including colocated fleet glyphs; `IClassicTerminal` separates character input and screen presentation. `ClassicConsoleTerminal` updates changed rows or emits snapshots for limited consoles. Orders/movement reuse Core operations. See [Classic terminal](ClassicTerminal.md) for findings and incremental scope.

`GameShell` parses commands using a switch, calls engine operations, directly changes visibility state, and accesses `State.FleetsSys`. It also embeds a separate `tf map` renderer. It currently has more responsibilities than a minimal command adapter.

`newgame` constructs a fresh `GameState`/`Game` with the current configuration and shell RNG, preserving the fog preference, then generates the galaxy and runs Classic player attributes and enemy initialization. `ClassicStartupFlow` renders a letter-only selection map, obtains a manual star letter or uses Core's automatic capacity selection, and translates quantity-prefixed C/S/B/W/V/R tokens into existing Core operations. It processes all tokens on a line before finalizing, including unaffordable tokens following budget exhaustion. Status shows only the player's fleet, technology/progress, and balance. The selection map neither reads enemy occupancy nor changes visibility. The flow uses line input; it does not reproduce raw terminal editing, 25-character truncation, or the original report subprompts. Q remains a selectable star; only the word `quit` exits the selection prompt.

After completed startup, the shell replaces its current game (`CurrentGame`); EOF or quit during startup exits without finalizing or replacing it. RNG draws already consumed by an abandoned candidate are not rolled back. The existing debug operations are unchanged; the shell reports Core lifecycle rejections (including blocked shared-start ticks and forbidden regeneration) and continues accepting commands. The debug startup/shell does not host the playable Classic combat/endgame loop; the default Classic interface does. `newgame` is explicit and is not invoked by `Program` automatically.

`ConsoleIO` implements `IGameIO`. `SystemRng` is an alternative adapter, not selected by `Program`.

Classic command parity retains the existing loop and terminal boundary. `IClassicTerminal` also exposes direct cursor placement and forced refresh. `FleetSystem.PreparePlayerCourse` owns C's pre-prompt cancellation; `SetCourse` reuses it, while the debug shell retains its earlier identifier-validation boundary. `ValidatePlayerSplit`, `SplitPlayerFleet` and `JoinPlayerFleets` own player fleet rules, sharing the existing merge/reference-rebuild helpers with movement. Classic UI parses tokens and refreshes reports; no new command abstraction is introduced. `ResearchRules.NextRequirement` exposes read-only requirements from existing investment tables. Exploration UI compares before/after fleet state after `Game.Tick`, without extra RNG or movement rules. See [command audit](ClassicCommandAudit.md) and [fleet commands](ClassicFleetCommands.md).

Landing reuses this boundary: `ValidatePlayerLandingFleet`, `PlayerLandingPlanets` and `ValidatePlayerLandingPlanet` expose the source's validation stages for prompt ordering; `LandPlayerTransports` revalidates and applies immediate ownership/population/IU/transport changes in Core. Empty fleets and board references use the existing helpers. No colony-count cache or deferred landing session is introduced. Classic L supplies one fleet key, automatic/manual planet selection and the first C token's quantity; its existing line reader supports row 21 without changing J/N/report input. See [landing](ClassicLanding.md) for source quirks and excluded systems.

`Game.Economy.cs` adds Classic begin/process/complete methods around existing movement, with post-movement revolt and original fourth-year growth before ordered player `ColonyInvestment` sessions. Core owns budget/costs/effects and queue/clock state; the CLI owns line tokens, help/report input and rendering. `ClassicScreen` displays the production clock and investment banner and defers temporary production fleet map markers until completion. No general event bus, economy service framework, global money model or persistence changes are introduced. Enemy-owned colony investment now runs automatically; undefined legacy capacity/slot conditions stop explicitly; see [economy audit](ClassicEconomy.md).

### Conquest.Tests

xUnit tests reference Core and CLI. `DummyIO` scripts commands/captures output; `SpyRenderer` checks renderer invocation. Tests cover configuration, RNG bounds, star structure, router dispatch, shell smoke sequences, fog flags, basic fleets, and selected snapshot fields.

There are no comprehensive Classic acceptance tests. Renderer-call tests do not verify real rendering, and snapshot tests do not establish restored-game usability.

### OriginalSource

Primary gameplay reference. The original loop performs player input, enemy decisions, movement, combat, periodic investment, annual updates, and game-over checks. A reproducible legacy build remains an investigation task; the .NET solution does not compile C.

### Graphics (future)

No graphics project or `IRenderer`/`IInput`/`IAudio` abstraction set is implemented. MonoGame, Godot, and Avalonia remain Phase 2 possibilities, not selected dependencies. Preserve UI-independent rules during Classic work.

## Key interfaces

- `IGameIO`: `ReadLine()`, `Write(string)`, `WriteLine(string = "")`.
- `IRng`: `Next(minInclusive, maxExclusive)` and `Reseed(seed)`.
- `ISeedableRng`: extends `IRng` with `Seed(int)`.
- `ICRandRng`: separate `Seed(uint)` and `NextInt(maxExclusive)` contract.
- `IMapRenderer`: `Render(IGameIO, GameState)`.

`IGameIO.ReadLine` returns a nullable string; `ConsoleIO` preserves EOF as null so both the command shell and interactive startup terminate cleanly when redirected input ends.

## Known inconsistencies and boundaries to resolve

- Sectors duplicate indices and object references. Board/stars are zero-based; fleet slots are 1-based. Some adapters still assume old conventions.
- CLI rendering consumes `ExploredBy`/`FogEnabled`; Core rendering consumes `Visible`/`RevealStars`. Discovery/reveal commands update the latter model and do not affect the active CLI map.
- Per-cell occupancy holds only one fleet per team, although fleets can share coordinates.
- Classic startup, debug placement, and surviving arrival retain the zero-based current star index in `TaskForce.Destination` with ETA zero, matching C's stationary `dest` convention; index zero is valid. Startup records the enemy in `Sector.TaskForces[0]`, marks only enemy exploration, and leaves `Sector.Tf` unchanged. General `tf_stars` counts are not stored; arrivals and reports query fleets directly. N allocates the first null-destination slot and removes emptied fleets; J clears child destinations while retaining inactive fields/counts as in C. Reuse resets counts and travel fields but preserves the original slot withdrawal flag. J's X-only location check deliberately preserves the documented C defect. J/N rebuild references without resetting unrelated flags or visibility; combat withdrawal now uses the same lifecycle helpers; see ClassicEncounters.md.
- Mutable configuration and public collections allow invalidation of allocation and cross-references.
- RNG and state are supplied separately to shell/engine, allowing inconsistent wiring.
- Turn/session ownership is now shared in `GameState`: `Game.Turn` reads `CompletedTurns`; production year starts at 1; the active Classic phase, investment budget and ordered queue survive new facades. A pending phase blocks direct/debug movement, repeated growth and early year completion. The shared irreversible `HasAdvancedTurns` marker still protects initialization. Debug `Game.Tick` increments completed turns without Classic economics/production-clock updates; direct fleet ticks increment no turn counter. Classic increments clocks only after movement/acknowledgements and all due player budgets finish. The displayed turn remains completed turns + 1. Wander indexing and normal endgame orchestration are implemented; existing snapshot DTOs omit all new clock/session data.

These are current limitations, not approved redesigns. Discuss significant state, occupancy, command-routing, visibility, or persistence decisions before implementation. See the [backlog](DevelopmentBacklog.md).

## Deferred original research behavior

Player economic research now reuses the startup investment rules and requirement tables; *R/V/W limits the applied amount to one next breakthrough. Enemy startup research remains implemented. General enemy research now preserves these `OriginalSource/research.c` quirks: `research()` runs at least once even with zero investment and selects a new enemy field after each iteration, including when the amount has been exhausted. Enemy weapons/range breakthroughs select a field inside `research_limited()` and again in the outer `research()`; velocity breakthroughs do not make the inner selection. The inner assignment to its field parameter is local. If no amount is consumed, the remaining investment is discarded after field selection. Range is the unconditional fallback even at its maximum level. Enemy investment/breakthrough decisions are now implemented; snapshots do not preserve research selection, player-startup/economy sessions, starting money or lifecycle state.

## Classic player startup boundaries

`GameConfig.StartingMoney` defaults to 30; transports remain independent. Core configuration supports nonnegative money, transports, and capacity for this session. Existing `GameConfig.Validate()` still exposes a clamped-zero `Capacity` for negative requests outside this path; it retains the requested value internally so Classic player startup rejects it instead of silently treating it as manual selection. Explicitly assigning a supported capacity replaces that request. No new CLI configuration options, configured-investment text, raw-key input, report subprompts, or 25-character line handling are introduced. The CLI adapter preserves purchase ordering and only finalizes after end-of-line budget exhaustion; actual battlestar cost is 70 despite the C startup help's conflicting 75. Negative budgets/capacities and overflowing quantities are deliberately unsupported instead of copying undefined C behavior or clamping. Direct mutation of public model collections remains a general invariant risk; startup operations validate lifecycle, board links, and starting fleet locations but do not redesign model ownership.
