## Exact order and destination rules

`inputmach` scans fleet slots 1..26, consulting the live table. Each stationary fleet computes Euclidean reachable distances once (distance within enemy range, zero for self/out-of-range), sends scouts, sends transports, orders remaining warships, then removes its empty slot. New travelling slots are not given another stationary order in that pass. Enemy travel uses `(int)((distance-.01)/enemyVelocity)+1`, not the player's rounded-distance formula. C leaves enemy origeta and coordinates at departure. A conversion defect was corrected: C's arriving enemy fleet slot survives and absorbs the first existing stationary fleet, whereas the previous C# code kept the existing slot. Arrival slot identity affects subsequent live-slot decisions/free-slot allocation and thus RNG order. The movement/first-turn regression now locks down the correct surviving slot. Arrival still updates only enemy exploration/seen ownership; no enemy exploration loss rolls are invented.

Transport score: unvisited enemy star 60; visited neutral/enemy/player **enemy-seen ownership** 40/30/0. On a visited non-player-seen world, add 40 if actual remaining room exceeds `40 - turn/2` (C displayed turn begins at 1; integer division). Subtract `(int)(2*distance+.5)`. Scan star then linked-planet order; strictly greater comparisons preserve ties. The second-best **planet** supplies `sec_star`, which can equal the best star.

When the best planet is current, **any** stationary player fleet blocks landing, including a scout. Actual player ownership also blocks it even if intelligence is stale. Otherwise land `min(transports, (capacity-population)/3)`. Zero old population makes ownership/enemy-seen ownership Enemy. Add one population and IU per transport; consume transports and re-score from scratch until no further landing occurs. This can reinforce enemy conquered colonies, unlike player L's refusal. It stops with fewer than three free places rather than forcing a planet full, and does not choose another target merely because its chosen current planet is blocked. Conquest flags and player-seen capacity are not reset by enemy landings.

For a remote best target, at least ten transports and a second candidate cause half (integer truncation) to go to the best, remainder to second. Otherwise all go to best. Each convoy takes one cruiser if available and the departure star is not underdefended. Underdefended means an enemy colony with IU > 10 and `6*AMB+MB < round(IU/15.0)`. Two convoys can go to the same star. New transport ownership is not granted merely on arrival; a subsequent enemy order phase performs landing. Scouts and warships can arrive on the same movement phase and merge with them.

Warship score: unseen 600. Otherwise enemy-seen Neutral 100; Enemy conquered 1000; Enemy unconquered 300 if `6*AMB+MB <= IU/15` and IU >= 8, else 0; player-seen conquered 400, unconquered 200. For an enemy-seen world with AMB >= 4 subtract 250. Visited capacity < 40 and IU < 15 subtract 100. Add **one rnd(20) per evaluated planet**, including current planets; add 250 at the current star and subtract 150 if a stationary enemy fleet is present. Use the best first-tied planet. This deliberately retains C's access to real population/industry/defenses behind some stale intelligence; it does not expose them to the player UI.

If staying at an actual enemy conquered colony with IU < 20, bombard using `min(enemyWeaponForce, 4*population)` and the shared original blast arithmetic. Refresh player-seen capacity only if the player has ships/colonies observing that star. Otherwise, larger conquered-colony garrisons may split and wander using the corrected reachable-star selection below. No modern strategic evaluation, route planning or difficulty adjustment is substituted.

## Enemy growth, spending and research

Investment is still every fourth turn, skipped on the final configured turn as C specifies. All owned planets grow before any budget opens. Enemy growth uses its own startup rate and the existing exact integer formula. Then each owned colony is processed in star/list order. Enemy budgets execute automatically; player budgets pause for original commands. An enemy colony after a player prompt sees that player's newly changed technology when choosing research. Growth/budgets are not replayed on EOF/resumption.

`inv_enemy` copies IU to its local balance (no global treasury). Use the first stationary enemy fleet, or allocate first free slot; produced ships are immediately added to it. Defense/research-only empty fleets are removed afterward. No unrelated player fleet is merged or modified.

1. While AMB == 0, unconquered, MB < capacity/20 and balance >= 8: build MB at cost 8.
2. With balance >= 70, AMB > 1, rnd(5) != 1 and rnd(7) <= AMB+3: build a **battlestar**, cost 70. The C comment calls this an AMB but the assignment is fleet `.b++`; code behavior wins.
3. With balance >= 35, unconquered and (AMB < 4 or rnd(2) == 2): buy AMB at 35. Four is a random gate, not a maximum.
4. While balance >= 9, draw rnd(12). 1/2: research 8. 3/4/10: cruiser at 16 if affordable, else MB at 8 if unconquered, else research 9. 11/12: infrastructure if population/capacity < .6 or (capacity >= 70/2 and IU < 80); otherwise mobilize transports unless conquered. Other choices buy infrastructure.
5. Infrastructure adds `min(3, 2*population-IU)`, debiting three per IU. Mobilization uses `min(rnd(2)+6, population-1)` and, if IU > 70, caps this to IU-70; debit transports from balance/population, clamp IU to `min(oldIU-transports, 2*newPopulation)`, add transports to fleet. No separate construction charge or abandonment is invented.
6. Remove an empty production fleet, then research the whole remainder, **even zero**. Some rnd(12) branches at infrastructure capacity or on conquered colonies make no progress; C rerolls, and so does this implementation. No invented forced purchase is inserted.

Research requirements/maxima are shared with existing player/startup tables. A call runs at least once, consumes only to the next breakthrough, then selects a new enemy field after every outer iteration. Weapons/range breakthroughs also select a field inside the limited call; velocity does not. That inner selection changes global `en_research`, not the caller's local field, and still consumes its RNG even though the outer choice follows. At a cap/no amount used, choose a field then discard the unconsumed amount. Selection checks `playerWeapons-enemyWeapons+5 > rnd(10)` with strict comparison, then enemy range/velocity **integer** division > rnd(3); Range is the fallback even at its cap. Short-circuited conditions consume no draws. No new RNG generator is introduced; full C PRNG identity remains unestablished.

## Regression coverage and changed files

### Correction: wander_bc indexing and the reported stoppage

The hands-on `Enemy orders stopped: Original wander_bc reads uninitialized slist[0]...` message came from the C# isolation guard, not an error raised by the C game. `MoveEnemyWarships` threw when the original conquered-garrison branch requested wandering. `IssueClassicEnemyOrders` retained `EnemyProcessingFailure`, so subsequent G inputs refused to replay partially executed orders. `ClassicScreen` clips the status line to its 79 printable columns, explaining the truncated message. Normal wandering no longer emits that error; the console layout is unchanged.

The original defect was rechecked across all `slist` declarations, writers and callers in the supplied source:

- `enemy.c:inputmach` declares automatic local `double slist[MAX_NUM_STARS+1];` without an initializer. It is not a zero-initialized global/static array. The zeroed dummy entries of some other C arrays do not initialize this separate array.
- `input.c:get_stars` receives that same base pointer and writes only indices **1..NUM_STARS**. Each gets the Euclidean distance or zero if beyond range. Self-distance is zero. No other enemy helper initializes/writes `slist[0]`; helpers receive/read the unchanged array. No supplied macro changes this indexing convention or provides automatic initialization.
- `wander_bc` counts nonzero entries at 1..NUM_STARS, draws `dest=rnd(count)`, then scans with `for (count=0, i=0; count!=dest; i++)`. The first test reads indeterminate `slist[0]`, which has no defined portable floating-point value. Even assuming it happened to be zero, the loop increments i after finding the selected reachable entry; `dest=i` then uses the **following** star and its distance. A last-star selection points beyond the active star range, and at the configured maximum beyond the array itself.
- Other enemy order routines scan stars from 1, use positive distances to exclude self/unreachable locations, and use the selected star's distance for ETA. `get_stars`' returned count can include self, but wander explicitly recounts only nonzero distances. There is no evidence that selecting the following star or counting a phantom dummy slot was intentional.

Chosen interpretation, as requested: select the rnd(count)-th **actual reachable noncurrent star**, ordered by star index. Conceptually the C scan should start at 1 and break on the selected entry, before incrementing past it. C#'s zero-based star A is a real star, so the implementation enumerates all valid C# indices with positive distances and maps the single bounded random choice to that list. No uninitialized-memory value is fabricated and no extra rejection sampling or strategic scoring is introduced. Historical output from a particular compiler/stack cannot be established from undefined behavior; the intended selection is strongly supported by the surrounding code, rather than confirmed by a running legacy binary.

`WanderEnemyWarships` retains the source guards and effects: only the existing conquered, IU >= 20 branch can call it; the rnd(4) trigger/short circuit (including the draw before guaranteed B>8 wandering) is unchanged. With no candidate it returns just as C's `count==0` branch does. Otherwise it draws rnd(reachableCount), allocates the first free enemy slot, transfers floor(B/2) and floor(C/2) with odd remainders left in the garrison, and transfers two T only when the parent has more than three. Scouts do not transfer. Existing `SendEnemyFleet` supplies departure visibility and `(int)((distance-.01)/velocity)+1`, with enemy origeta/coordinates unchanged. Normal movement then advances the child in that same turn. Combat, growth, production and clock sequencing are unchanged. The original C reference files are retained verbatim.
